# VENDOR-ISSUES.md: where the A1580 differs from its own documentation

Material for tickets to the A1580 developer. One entry per observation: what the vendor
document or example says (cited as in `PROTOCOL.md`: `SC` = `SCPI_COMMANDS.md`, `EX` = the
vendor example script), what the device did, and how to reproduce it. Entries are facts
measured on one A1580-HF; where the cause is a guess, it is marked as a guess.

Classes: **BUG?** looks like a firmware defect; **DOC** the document or example is wrong or
out of date; **LIMIT** an undocumented limitation; **INFO** harmless difference worth
knowing.

All SCPI lines were sent to TCP 5025 with `\r\n`; replies are shown exactly as received
without the trailing `\r\n`.

## Session 2026-10-05, firmware `1.16 (861f022a)`, phase A (read-only queries)

| # | Class | Subject | Vendor material says | Device does | Reproduce |

| A1 | LIMIT | Input buffer of roughly 256 bytes; on overrun the commands are dropped and a query is never answered | Nothing about an input buffer or pacing. | 25 lines `ZZZ:NOPE01` ... `ZZZ:NOPE25` plus `SYST:ERR:COUN?` (about 320 bytes) written without reading: only the first line was processed (`-113,"Undefined header;ZZZ:NOPE01"`), the queue then held `-363,"Input buffer overrun"`, all other lines were discarded and the query was never answered (5 s timeout), so a client blocks. ## Session 2026-10-05, firmware `1.16 (861f022a)`, phase B (pulser off, acquisition, nothing connected to IN/OUT)

Settings for the acquisitions: `TRAN:ENAB OFF`, `DATA:LENG 1024`, `FREQ 100 MHZ`, `TRIG:MODE INT`,
`TRIG:INT 10 MS`; data socket on the port from `DATA:PORT?` (2758), `STAR AUTO`, read, `STOP`.

| # | Class | Subject | Vendor material says | Device does | Reproduce |
|---|---|---|---|---|---|
| B1 | BUG? | The power-on `DATA:LENG` cannot be written back | Range 1024 to 36864 (SC:125-153). | After power-on `DATA:LENG?` -> `114688`. `DATA:LENG 1024` is accepted. `DATA:LENG 114688` is then refused with `-224,"Illegal parameter value"` and the value stays 1024. So the device starts with a value its own setter rejects; a client that saves the settings and restores them afterwards cannot return the device to its power-on state (only a power cycle does). The setter range is exactly the documented one: `DATA:LENG MAX` -> 36864, `MIN` and `DEF` -> 1024, 36864 accepted, 36865 / 65536 / 114688 / 1023 refused with -224 and the old value kept (no clamping), 1025 accepted. So it is the power-on value 114688 that is out of range. What the device streams at that length is in B8. | power-cycle; `DATA:LENG?`; `DATA:LENG 1024`; `DATA:LENG 114688`; `SYST:ERR?`; `DATA:LENG?` |
| B2 | DOC | `AVER:COUN` is an exponent, and `ascan_count` does not show it | `AVER:COUN`: "Acquisitions per averaged vector", 0 to 8 (SC:803-825). The REST document says "0-8 (power of 2)" for `accumulations` (RA:143). No document explains the header field `ascan_count`. | With an open input the noise standard deviation per packet was 3.59 counts at `AVER:COUN 0` and 0.94 counts at `AVER:COUN 4`, ratio 0.26. A mean of 4 acquisitions would give 0.5, a mean of 16 gives 0.25: the count is 2^N and the result is a mean, not a sum (assuming uncorrelated noise). The header `ascan_count` was 1 in both cases and the packet interval stayed 10.0 ms. | acquire 10 packets with `AVER:COUN 0` and with `AVER:COUN 4`, compare the noise |
| B3 | DOC | Header length field | `length_lo` / `length_hi` have no stated meaning. | With `DATA:LENG 1024` every packet is 2076 bytes (28-byte header plus 1024 int16 samples) and the header carries `length_lo` = 1040, `length_hi` = 0. The field is the sample count plus 16 at every length tried: 1024 -> 1040, 2048 -> 2064, 8192 -> 8208, 36864 -> 36880 (packet sizes 2076, 4124, 16412, 73756 bytes = 28 + 2 x length). What the 16 stands for is not known; a client that takes this field as the sample count reads 16 samples too many. | acquire one packet at `DATA:LENG 1024`, decode the header |
| B4 | INFO | `STOP` and the data socket | "Open the data socket before `STAR AUTO`" in one document, the opposite order in another. Nothing about packets after `STOP`. | After `STOP` two more packets arrived within 20 ms, then the socket went idle and stayed open (not closed by the device). A data socket connected after `STAR AUTO` received packets 20 ms after connecting. Both orders work. | as described |
| B5 | INFO | Setting change while streaming | Not documented. | `GAIN 6` during `STAR AUTO`: no error, `GAIN?` -> `6`, the stream went on with the same packet size. | as described |
| B6 | INFO | Data connection and SCPI connection | Nothing. | Unlike a second connection to port 5025 (A2), the data connection on port 2758 does not disturb the SCPI connection; data connections were opened and closed five times in one SCPI session. | as described |
| B7 | DOC | Header `ctp[0]` | "CTP timing array" or "X,Y,Z coordinates" (the documents disagree). | In `TRIG:MODE INT`, `ctp[0]` is a packet counter with the same value as `packet_number` (35, 36, ... 112 seen), `ctp[1]` and `ctp[2]` are 0, the reserved bytes are 0. Whether `ctp[0]` goes on past 255, where the one-byte `packet_number` must wrap, is not measured yet. The counter is not reset by `STOP` / `STAR AUTO`. | decode the header of consecutive packets |
| B8 | BUG? | What is streamed at the power-on `DATA:LENG` 114688 | Maximum 36864 samples. | After power-on (`DATA:LENG?` -> `114688`, pulser switched off, `TRIG:INT 10 MS`, nothing connected) the device streams 100 packets per second of 229404 bytes = 28 + 2 x 114688 (22.9 MB/s); header `length_lo` = 49168, `length_hi` = 1, together 114704 = 114688 + 16. Only part of each packet is data: samples 81906 to 114687 are exactly 0 (81906 = 5 x 16384 - 14, as if an 81920-word buffer included the 14 header words), and inside the first 65522 samples a long stretch holds one constant value (30 counts) instead of noise, with a different start in every packet; the stretch always ends at sample 65521 (= 65536 - 15). Elsewhere the samples are the usual noise (mean 11, std 3.6 counts). So acquisitions at the power-on length are partly invalid. | power-cycle; `TRAN:ENAB OFF`; `TRIG:INT 10 MS`; open port 2758; `STAR AUTO`; look at one packet |
| B9 | INFO | Automatic averaging delay follows `TRIG:INT` | See A10. | Confirmed: with `AVER:DEL:CONS:AUTO` on, `TRIG:INT` 1 s gives `AVER:DEL:CONS?` -> `0.99992925`, `TRIG:INT 10 MS` gives `0.00992925`: the trigger interval minus 70.75 us in both cases (`AVER:COUN` 0, `FREQ` 100 MHz). The document says the value is computed "from the averaging count and sampling rate". | the queries |

## Session 2026-10-05, firmware `1.16 (861f022a)`, phase C (pulser on, two 50 kHz transducers) and `*RST`

| # | Class | Subject | Vendor material says | Device does | Reproduce |
|---|---|---|---|---|---|
| C1 | BUG? | `*RST` resets nothing | `*RST`: "Reset the instrument" (SC:37); every command has a `DEFault` value. | Six settings were moved away from their power-on values (`GAIN 6`, `TRIG:INT 10 MS`, `AVER:COUN 2`, `TRAN:FREQ 50 KHZ`, `FILT:HPAS:IND 2`, `TRIG:DEL 0 NS`, each read back), then `*RST` was sent: no error, the next query was answered 59 ms later, and all 27 settings read exactly as before `*RST`, also 2 s later (`GAIN?` -> `6`, `TRIG:INT?` -> `0.01`, `AVER:COUN?` -> `2`, `TRAN:FREQ?` -> `50000`, `FILT:HPAS:IND?` -> `2`, `TRIG:DEL?` -> `0`, `DATA:LENG?` -> `8192`). `TRAN:ENAB` stayed `0`, `DATA:PORT?` stayed `2758`. So `*RST` returns the device neither to the documented defaults nor to its power-on state. Whether it stops a running acquisition or clears the error queue was not tested. | set any value, `*RST`, query |
| C2 | INFO | Stale data after a change of `DATA:LENG` | The example sends `MEM:CLEar` before `STAR AUTO` without saying why. | The first stream after `DATA:LENG` was changed from 114688 to 8192 began with 98332 bytes (6 x 16384 + 28) that did not frame as 8192-sample packets; good packets followed. Whether `MEM:CLEar` prevents it is not measured yet. | power-cycle; `DATA:LENG 8192`; open the data port; `STAR AUTO`; look at the first bytes |
| C3 | INFO | `TRIG:DEL` and time zero | "Delay between a trigger event and the acquisition" (SC:460-489); what sample 0 is, is not stated. | With two 50 kHz transducers face to face the received signal starts 3 us after sample 0, and it stays on the same samples for `TRIG:DEL` 0, 1000 US and 2000 US: the burst and the record are delayed together, sample 0 is the start of the burst. Worth one sentence in the manual. | as described |
| C4 | INFO | Automatic averaging delay, formula | See A10 and B9. | Third point: `TRIG:INT 10 MS` with `AVER:COUN 2` gives `AVER:DEL:CONS?` -> `0.00242925`. All three points fit `TRIG:INT / 2^AVER:COUN - 70.75 us`. | the queries |
| C5 | LIMIT | Exact input-buffer limit, single line | See A1. | One line of L bytes in total (terminator included), then `SYST:ERR?`: L = 100, 150, 200, 250, 254, 255 -> `-113` (parsed); L = 256, 257, 258, 260, 300, 400, 600 -> `-363,"Input buffer overrun"` (discarded). The buffer is 256 bytes; the longest accepted line is 253 characters plus CRLF. A `GAIN:TGC:ARB` list can be longer than that. The text of the `-113` entry is cut at 262 characters. | as described |
| C6 | INFO | Stale bytes and `MEM:CLEar` (sharpens C2) | See C2. | Not reproduced with legal lengths: stream at 36864, `STOP`, data socket closed at once, `DATA:LENG 8192`, new stream: well framed from byte 0 in three trials, one of them with `MEM:CLEar` before `STAR AUTO`. So the stale bytes of C2 belong to the stream at the power-on length 114688 (B8); what `MEM:CLEar` is needed for is still not known. | as described |
